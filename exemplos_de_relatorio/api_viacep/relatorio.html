Melhorias e ideias 6

Geradas por IA a partir dos prints e do log. São sugestões: avalie com o time antes de transformar em requisito.

Sugestão · Usabilidade Prioridade Média

Exibição do tempo de resposta em todos os passos de requisição

Adicionar o tempo exato de resposta em milissegundos para todas as requisições HTTP no log de execução (e não apenas na validação do CT01), facilitando a identificação de gargalos de performance e diagnósticos rápidos pelo time de QA.

Base: Passos 1, 9, 11 e 15 do caminho de execução

Sugestão · Texto Prioridade Média

Padronização da casing na validação do atributo booleano de erro

No passo 13, a checagem é descrita como 'erro = True' (com maiúscula), enquanto no retorno do JSON original do ViaCEP a chave/valor é representada em minúsculo ('erro' = 'true' ou valor booleano true). É importante padronizar a escrita no log para refletir a especificação real da API.

Base: Passo 13 ('Verificar o campo JSON erro = True')

Sugestão · Funcionalidade Prioridade Alta

Restrição do código de status HTTP na consulta de usuários

No passo 21 do CT04, a asserção aceita qualquer status no intervalo [200, 299]. Para consultas GET de recursos existentes, deve-se validar estritamente o status HTTP 200 OK, evitando que respostas como 204 (No Content) ou 202 (Accepted) passem indevidamente como sucesso de busca.

Base: Passo 21 ('Verificar se o status HTTP é [200, 299]')

Sugestão · Funcionalidade Prioridade Média

Ajuste do SLA de tempo de resposta para consultas de API

O CT01 utiliza um limite máximo de tolerância de 5000 ms. Para requisições de consulta de CEP em microsserviços, recomenda-se reduzir o threshold de tempo limite para 1000 ms ou 2000 ms, garantindo a detecção precoce de degradação de desempenho.

Base: Passo 8 ('Verificar se respondeu em até 5000 ms')

Sugestão · Funcionalidade Prioridade Média

Validação completa de schema JSON (JSON Schema Validation)

Substituir ou complementar a verificação pontual de campos isolados (ex: 'cep', 'localidade', 'address.city') por uma validação completa baseada em JSON Schema, garantindo a verificação rigorosa de tipos, campos obrigatórios e estrutura de contrato das APIs.

Base: Passos 4, 5, 6, 7, 17, 18 e 22

Sugestão · Acessibilidade Prioridade Baixa

Padronização de corpos de resposta de erro HTTP 400 (Problem Details)

Garantir que a resposta da API para CEP com formato inválido (HTTP 400) retorne um payload estruturado no padrão RFC 7807 (Problem Details), fornecendo mensagens claras e descritivas legíveis por leitores de tela em painéis/dashboards que consomem a API.

Base: Passo 10 ('Verificar se o status HTTP é 400')
